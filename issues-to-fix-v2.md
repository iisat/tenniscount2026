# Высокий приоритет

- [ ] **1. Ручная правка счёта сета может уронить приложение**

  В `SetEditDialog` пользователь может выставить недостижимый терминальный счёт,
  например `7:4`, `8:5`, `10:4`, и кнопка «Применить» остаётся активной.

  Далее UI вызывает:

  `ScoreboardScreen -> MatchViewModel.editSetScore() -> MatchEngine.editSetScore()`

  `MatchEngine.editSetScore()` использует `require(...)` и для такого значения бросает
  `IllegalArgumentException`. Исключение из ViewModel не перехватывается, поэтому это
  реальный пользовательский crash path.

  **Что исправить:**

  1. Добавить единую domain-валидацию ручного счёта сета.
  2. В `SetEditDialog` заранее определять, можно ли применить выбранный счёт.
  3. Для недопустимого значения:
     - показывать понятное предупреждение;
     - отключать кнопку «Применить».
  4. UI-операции не должны падать из-за `require(...)`.
     Для публичного пути ручной правки вернуть контролируемый результат
     (`Result`, sealed result или аналог) либо безопасно обработать ошибку на границе ViewModel.
  5. Не дублировать разные правила в UI и domain: источник истины для валидности должен быть один.

  **Ожидаемое поведение:**

  - `5:4`, `6:5`, `7:6` — допустимые незавершённые состояния;
  - `6:0..6:4`, `7:5`, `8:6`, `9:7` — допустимые завершённые сеты;
  - `7:4`, `8:5`, `100:1` — не применяются и не приводят к падению приложения.

  **Тесты:**

  - domain-тесты валидатора;
  - regression-тест `editSetScore(7, 4)` — отсутствие crash и контролируемый отказ;
  - тесты допустимых пограничных значений.

  **Код:**
  - `app/src/main/java/com/tenniscount/app/ui/scoreboard/ScoreboardScreen.kt`
  - `app/src/main/java/com/tenniscount/app/ui/MatchViewModel.kt`
  - `app/src/main/java/com/tenniscount/app/score/MatchEngine.kt`
  - `app/src/main/java/com/tenniscount/app/score/SetState.kt`

- [ ] **2. Синхронизировать голосовой парсер, Vosk grammar и спецификацию**

  Текущие `ScoreParser`, `VoskRecognizer`, `task.md` и README описывают разное поведение.

  Основное фактическое расхождение: `task.md` и README требуют поддержку сокращённого
  объявления одного числа:

  - «пятнадцать» = `15:0`;
  - «тридцать» = `30:0`;

  но текущий `ScoreParser` специально возвращает `null` для одного числа, а Vosk grammar
  не содержит одиночных числовых фраз. Unit-тесты сейчас закрепляют именно это
  противоречащее спецификации поведение.

  Дополнительно parser сначала обрабатывает `numbers.size >= 2`, а уже потом команды.
  Поэтому сам parser для фразы вроде «тридцать пятнадцать отмена» выберет счёт,
  хотя команда `отмена` должна иметь приоритет.

  В старом аудите также упоминались голосовые команды `сет` и `матч`.
  В текущей архитектуре:
  - сет завершается автоматически по правилам;
  - матч завершается вручную кнопкой;
  - в текущей Vosk grammar слов `сет` и `матч` уже нет.

  **Решение для v2:** не добавлять `сет`/`матч` как голосовые команды без отдельного
  продуктового решения и определённой семантики. Удалить их из списка поддерживаемых
  голосовых команд в `task.md`, чтобы спецификация соответствовала продукту.

  Семантика `больше` / `меньше` **правильная и менять её не нужно**:
  по спецификации счёт объявляет подающий, поэтому:
  - `больше` = advantage подающего;
  - `меньше` = advantage принимающего.

  **Что исправить:**

  1. Вернуть сокращённые объявления одного числа согласно `task.md`:
     - `пятнадцать` -> `15:0`;
     - `тридцать` -> `30:0`;
     - `сорок` -> `40:0`;
     - определить и протестировать поведение для `ноль` / `нуль`.
  2. Добавить одиночные допустимые числовые фразы в ограниченную Vosk grammar.
  3. Командам дать приоритет над числами.
     Как минимум `отмена` / `отмени` должны выигрывать у числовой части фразы.
  4. Фразы с более чем двумя числами не должны молча использовать первые два:
     неоднозначный ввод отклонять.
  5. Привести комментарии в `ScoreParser`/`VoskRecognizer`, unit-тесты, `task.md`
     и README к одному поведению.
  6. Удалить `сет`/`матч` из `task.md` как якобы поддерживаемые voice commands,
     если отдельная реализация этих команд не планируется.

  **Минимальные regression-тесты:**

  - `пятнадцать` -> `15:0`;
  - `тридцать` -> `30:0`;
  - `пятнадцать отмена` -> `Undo`;
  - `тридцать пятнадцать отмена` -> `Undo`;
  - фраза с 3+ числами -> отклонение;
  - `больше` -> advantage server;
  - `меньше` -> advantage receiver;
  - все команды, присутствующие в grammar, имеют обработчик в parser.

  После изменения grammar провести короткий smoke test на физическом устройстве:
  одиночные числа не должны давать неприемлемый уровень ложных срабатываний.

  **Код:**
  - `app/src/main/java/com/tenniscount/app/speech/ScoreParser.kt`
  - `app/src/main/java/com/tenniscount/app/speech/VoskRecognizer.kt`
  - `app/src/test/java/com/tenniscount/app/speech/ScoreParserTest.kt`
  - `task.md`
  - `README.md`
  - `README.RU.md`

# Надёжность и release readiness

- [ ] **5. Добавить тесты Android/service boundary**

  Чистый score/domain слой покрыт тестами значительно лучше, чем Android boundary,
  хотя наиболее опасные ранее найденные проблемы были связаны именно с lifecycle,
  foreground service, разрешениями и запуском recognizer.

  Старое требование тестировать malicious runtime ZIP больше неактуально:
  Vosk-модель теперь поставляется в APK, а распаковка build-time архива уже содержит
  SHA-256 и canonical-path защиту.

  **Добавить минимальное покрытие для актуальной архитектуры:**

  1. отказ в `RECORD_AUDIO`;
  2. ошибка запуска recognizer / AudioRecord;
  3. асинхронная ошибка recognizer после успешного старта;
  4. pause/resume/stop foreground service;
  5. пересоздание Activity/ViewModel и синхронизация с `ListeningController`;
  6. restart foreground service / `intent == null`;
  7. восстановление незавершённого матча после пересоздания процесса;
  8. ошибка/прерывание копирования bundled Vosk-модели из assets;
  9. корректное освобождение recognizer/service при повторных start/stop.

  Использовать instrumented tests и/или Robolectric там, где это оправдано.
  Не пытаться искусственно перенести всё в JVM unit-тесты.

  **Критерий:** исправления lifecycle/service не должны зависеть только от ручного тестирования.

# Технический долг — после закрытия функциональных и release-задач

  - матчем и UI state;
  - SharedPreferences;
  - Room/history;

  - audio focus;
  - сигналами;
  - foreground service;
  - Vosk lifecycle;

  - `SettingsRepository` / `SettingsStore`;
  - `MatchRepository`;
  - `AudioFeedbackManager`;
  - speech/listening orchestration;
  - Telegram publisher/configuration boundary.

  `MatchViewModel` должен остаться orchestration/UI-state слоем.

  Рефакторинг выполнять небольшими этапами с тестами, без изменения поведения.
