# Bugfix task: prevent split voice score from corrupting game winner

## Problem

Во время ведения счёта голосом иногда гейм засчитывается не тому игроку.

Наблюдаемый сценарий:

- строгая валидация счёта **выключена**;
- подаёт Player 2;
- фактический счёт — `30:40` в формате `подающий : принимающий`;
- пользователь произносит: `30 40`;
- затем произносит: `гейм`;
- ожидается победа Player 1 (принимающего);
- иногда гейм засчитывается Player 2 (подающему).

Проблема несколько раз воспроизводилась именно после `30:40`. После `15:40` аналогичное поведение не наблюдалось.

Предполагаемая первопричина находится на стыке Vosk и `ScoreParser`.

## Root cause

Сейчас `ScoreParser` принимает одно распознанное число как полноценное объявление счёта:

```kotlin
numbers.size == 1 -> {
    val serverPoints = GameState.pointsToCount(numbers[0]) ?: return null
    VoiceCommand.Score(
        Announcement.Points(serverPoints, 0)
    )
}
```

То есть:

```text
"пятнадцать" -> 15:0
"тридцать"   -> 30:0
"сорок"      -> 40:0
```

Это было добавлено как workaround на случай, когда Vosk слышит только первое слово объявления вроде `15 0`.

Однако при непрерывном распознавании двухсловная фраза может быть разделена на несколько final result.

Например пользователь произносит:

```text
тридцать сорок
```

а recognizer последовательно отдаёт:

```text
"тридцать"
"сорок"
```

При выключенной strict validation приложение применяет оба результата:

```text
"тридцать" -> 30:0
"сорок"    -> 40:0
```

Последним внутренним состоянием становится `40:0` в пользу подающего.

Следующая команда:

```text
гейм
```

использует `currentGame.announcedWinner`, видит преимущество подающего и ошибочно засчитывает ему гейм.

Это объясняет наблюдаемый сценарий `30:40 -> гейм`, не требуя предполагать, что Vosk перепутал порядок `30 40` и `40 30`.

## Required fix

### 1. Запретить single-number score announcements

Удалить из `ScoreParser` поддержку одиночного числа как полного счёта.

Одиночные результаты:

```text
"ноль"
"пятнадцать"
"тридцать"
"сорок"
```

не должны изменять состояние матча.

Для обычного счёта должны приниматься только полноценные объявления с двумя значениями:

```text
ноль ноль
пятнадцать ноль
ноль пятнадцать
тридцать пятнадцать
тридцать сорок
сорок тридцать
...
```

Специальные команды (`ровно`, `больше`, `меньше`, `гейм`, `сколько`, `отмена` и т. п.) продолжают обрабатываться отдельно как сейчас.

### 2. Передавать Vosk grammar как набор допустимых фраз

Сейчас grammar фактически представляет собой vocabulary из отдельных слов.

Нужно формировать grammar из полных допустимых команд/фраз, например:

```text
"ноль ноль"
"ноль пятнадцать"
"ноль тридцать"
"ноль сорок"

"пятнадцать ноль"
"пятнадцать пятнадцать"
"пятнадцать тридцать"
"пятнадцать сорок"

"тридцать ноль"
"тридцать пятнадцать"
"тридцать тридцать"
"тридцать сорок"

"сорок ноль"
"сорок пятнадцать"
"сорок тридцать"

"ровно"
"больше"
"меньше"
"гейм"
"сколько"
"отмена"
"отмени"
```

Список комбинаций лучше генерировать программно, чтобы не дублировать определения допустимых значений счёта.

Если `[unk]` сейчас используется и нужен для нормальной работы recognizer — сохранить его.

### 3. Не менять core scoring logic

`GameState.announcedWinner`, `MatchEngine.winGame()` и логика преобразования `server : receiver -> Player.ONE / Player.TWO` выглядят корректно.

Исправление должно быть на уровне speech recognition/parsing, а не через специальные исключения вроде:

```text
если счёт 30:40, считать победителем принимающего
```

Такие workaround'ы запрещены.

## Regression tests

Добавить тесты минимум на следующие сценарии.

### ScoreParser

Одиночные числа больше не являются счётом:

```text
"ноль"       -> null / ignored
"пятнадцать" -> null / ignored
"тридцать"   -> null / ignored
"сорок"      -> null / ignored
```

Полные объявления продолжают работать:

```text
"тридцать сорок" -> Score(30, 40)
"сорок тридцать" -> Score(40, 30)
"пятнадцать сорок" -> Score(15, 40)
```

Специальные команды не ломаются:

```text
"ровно"
"больше"
"меньше"
"гейм"
"отмена"
```

### Regression: split recognition

Сымитировать последовательность callback'ов:

```text
initial state: 30:30
server: Player 2
strict validation: OFF

recognition #1: "тридцать"
recognition #2: "сорок"
recognition #3: "гейм"
```

После исправления первые два одиночных recognition result не должны превращаться в `30:0` / `40:0`.

Команда `гейм` не должна ошибочно отдавать гейм Player 2 из-за split recognition.

Добавить зеркальный тест для Player 1.

### Normal game-point flow

Проверить нормальный сценарий целиком:

```text
server = Player 2
voice = "тридцать сорок"
voice = "гейм"

expected winner = Player 1
```

И зеркальный:

```text
server = Player 1
voice = "тридцать сорок"
voice = "гейм"

expected winner = Player 2
```

Также проверить:

```text
server = Player 2
voice = "пятнадцать сорок"
voice = "гейм"

expected winner = Player 1
```

## Acceptance criteria

- Одиночное распознанное число никогда не изменяет текущий счёт.
- `30 40` распознаётся и применяется только как единое полное объявление `30:40`.
- Split recognition `тридцать` + `сорок` не может превратить счёт в `40:0`.
- При выключенной strict validation split recognition также безопасен.
- При `server = Player 2`, `30:40 -> гейм` победителем становится Player 1.
- При `server = Player 1`, `30:40 -> гейм` победителем становится Player 2.
- Поведение `15:40`, `40:30`, `ровно`, `больше`, `меньше`, `гейм`, `сколько`, `отмена` не регрессирует.
- Vosk grammar содержит полноценные допустимые фразы, а не только отдельные числовые слова.
- Добавлены regression tests на split recognition и на `30:40 -> гейм` для обоих подающих.

## Scope

Исправление нужно внести в общую scoring/speech логику, чтобы оно применялось не только к `feature/telegram_count_publish`, но и после переноса/merge в `develop` и далее в `main`.

Telegram publishing к этому багу отношения не имеет и не должен модифицироваться в рамках данного fix.
